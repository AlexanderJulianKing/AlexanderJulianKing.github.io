How to trick an AI agent

Why coding agents that verify the data deeply still report confident wrong answers

Somewhere in a payments company’s records is a merchant whose identifying code is, by sheer chance, NULL. A real merchant, with real disputes, and more of them than anyone else. Unfortunately, this is very bad for many data analysis tools, which use NULL as a signifier of a missing value. When an AI coding agent loads the file with the common data management tool pandas at default settings, that merchant’s code silently becomes missing data, and the busiest merchant in the company vanishes from every per-merchant count that follows. pandas reports no errors. The runner-up looks like a perfectly plausible answer. In my study, agents given no warning fell for this in 49 of 50 runs.

Three traps

i

Notice what these three traps share. Nothing is hidden from the agent: the reformatted log lines are in the file it was told to read, the timestamp column is in the table it aggregated, the NULL merchant is in plain sight. Each trap only violates a precondition of the tool the agent habitually reaches for, and the violation produces no error, just a wrong number.

(2)

Agents catch almost everything else

ii

This is the counterintuitive part. Modern coding agents are genuinely hard to fool. I tried to trick them with things that would normally trick regular LLM chatbots: misleading documentation, false bug reports, leaky features, and statistical pitfalls. The agents almost never fell for it.

What does trick them is a specific blind spot. Agents are fantastic at verifying the data, but they rarely double-check how it interacts with the tools they use. Each tool carries a precondition, an assumption the data has to satisfy for the tool to behave, and a trap works by violating that precondition somewhere no routine check looks. The missing step: confirming your tool actually touched every record in scope.

(3)

What 1,000 runs show

iii

I generated twenty tasks that fit these traps: 10 with Claude Fable and 10 with GPT-5.6 Sol. If an agent returns the trap value I planted, I counted that as the agent falling for the trap.

If agents were merely sloppy, wrong answers would scatter. They don’t. Across the full suite, 785 runs produced an answer that was wrong, and 780 of them produced the exact planted trap value.

Strangely, agents that notice the anomalies can still fall for the traps. Noticing that the data will produce anomalous results is not always enough to divert their data-processing workflow.

From a falling run · storage-occupancy task…the flagged record “introduce[s] no double-counting”; the agent wrote this about the planted record, immediately before using the poisoned figure in its final answer.
(4)

What helps, measured

iv

The first fix I tested was making the agents think harder, using the reasoning-effort setting both coding agents expose. Of the two flagships, more reasoning helped Opus a little and GPT-5.5 not at all.

The second fix is a prompt change: one paragraph of plain instructions, pasted above the task. I re-ran the flagships with it on the tasks each had fallen on in the first, Fable-designed half. Each ran at the setting it had used throughout development: GPT-5.5 at “xhigh” (my configuration at the time) and Opus 4.8 at “high” (the default). Fall rates dropped roughly fourfold. However, runs with the warning burned a median of 2.5 times the tokens, up to 4.2 times on some tasks. Here it is in full.

The preamble
You are a senior data analyst who has been burned by bad numbers before. Before you report any figure, sanity-check your own method: (a) Reconcile the number of records your parsing or filtering matched against the total number of records in scope, and account for every record that was dropped. (b) Treat any zero, gap, or surprising value in your intermediate results as a possible bug in your method, not as a fact, until you have confirmed it. (c) Verify that your assumptions about data format, units, and structure hold across the entire dataset, not just the first rows you looked at. With that discipline, complete the following task.
(5)

An old pattern, one level up

v

There is precedent for this in ordinary chatbots. Benchmarks like SimpleBench showed that language models stumble when a question looks like a familiar template with one detail changed: the model follows the well-worn path from its training data straight past the detail. As reasoning training improved, models got substantially better at those questions.

The traps in this study look like the same failure transposed to agents. Agents learn standard workflows in training: read the file, group, count, report. Every trap here leaves that workflow looking normal while quietly breaking one of its assumptions, and the agent follows the familiar procedure straight past the break, the way chatbots once sailed past the odd detail in a word problem.

Chatbots got better at their trick questions as reasoning improved. Agents will probably get better at these. Whether the improvement comes from models learning to audit their own instruments, or from harnesses that force the audit, remains an open question.
